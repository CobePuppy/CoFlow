# 汇流 技术设计与 MVP 验收规范

版本：1.0 / 日期：2026-10-16 / 状态：待实施基线

### 2026-10-16 实施修订

后端和数据库已实现并通过隔离 PostgreSQL 集成验证；前端已使用腾讯 Ardot 完成设计并接入真实 API。当前实施情况、命令、验证及限制以 README、`03-后端接入说明.md`、`04-前端设计交接.md` 为准；3 个核心浏览器 E2E 场景已通过；未覆盖的范围与实现差异仍以以下修订为准。

为在当前小团队 MVP 中集中保证状态机、乐观锁和事务一致性，需求/方案/审批/开发/测试/评论等任务内记录采用 Task JSONB 聚合，提交历史用数据库触发器强制追加保护；文档单独保存历史，团队、项目、会话、邀请、附件、通知、审计和幂等为独立表。复合外键、表达式索引和归档写入保护由 SQL 迁移维护。此实现调整了第 7 节的一表一实体方案，后续可在保留不可变版本语义的前提下拆表。

NestJS 作为 HTTP 宿主，路由集中组织；领域状态机、输入校验和附件校验已拆开，尚未完成第 6 节列举的全部独立 Nest 模块拆分。项目内任务筛选暂在服务端读取后处理，适用于 MVP 数据规模。

API 中任务与通知列表返回分页对象，团队/项目/成员/文档/待办/时间线目前返回数组；成员角色更新使用 POST upsert，并新增 DELETE 移除成员接口。方案与阻塞快捷接口统一转入业务动作处理器。邀请增加预览与受邀注册接口。具体返回类型和字段见后端接入说明，避免前端按原表格推断不存在的契约。

阻断缺陷现阶段采用更严格的“必须关闭”规则，未实现双人联合降级；邀请注册界面和正式视觉设计已实现，核心浏览器 E2E 已通过；工作台拖拽尚未开放。主业务状态机、职责分离和旧审批失效规则保持原定义。

## 1. 目标与范围

汇流 为 5～50 人团队提供从需求到交付的协作闭环。用户已确定的核心流程为：需求提出（产品）→ 给出解决方案（研发）→ 评估解决方案（产品/测试）→ 开始开发 → 开发完成 → 测试（测试运维）。

本文在该流程上补充产品验收关闭、需求草稿、取消与退回机制，作为可调整的默认设计。产品与测试双人确认、技术栈、团队规模也属于实施默认值，并非用户已明确指定的细节。

参考地址：https://fcncvoyreb8p.feishuapp.com/app/app_17b6pxwde0x 。该页面尚未成功读取，本文不声明与其功能或界面一致。

MVP 包括团队、项目、任务交付、文档、评论附件、站内通知和基础统计。暂不包括音视频、独立聊天、多人实时编辑、可视化流程编排、生产发布流水线、外部消息集成和 AI 自动执行。

## 2. 角色与授权

权限由团队身份、项目成员资格及项目角色共同决定。项目可同时授予多种角色，但单个任务的评估职责必须满足分离约束。

| 角色 | 主要职责 |
|---|---|
| 团队管理员 | 成员邀请、团队设置、项目管理；无权绕过业务审批 |
| 产品 PRODUCT | 需求提交、需求变更确认、产品评估、产品验收 |
| 研发 ENGINEER | 技术方案、开发、自测、提测、修复 |
| 测试 QA | 测试评估、测试执行、缺陷、测试结论 |
| 运维 OPS | 环境准备、部署验证；授权为任务测试负责人时可提交测试结论 |

任务指定产品负责人、研发负责人、产品评估人、测试评估人、测试负责人。提交需求前必须指定全部负责人；产品评估人与测试评估人必须是不同账号，且均不得为方案提交人。人数不足时在配置页面给出原因，禁止自动豁免。

项目归档后业务只读。成员移除前必须完成其未结束任务的责任转交；历史操作保留身份快照。跨团队资源默认不可见，返回 404；同团队资源上操作权限不足返回 403。

## 3. 状态机

| 状态代码 | 中文 | 当前主要处理人 |
|---|---|---|
| DRAFT | 需求草稿 | 产品负责人 |
| SOLUTION_PENDING | 待出方案 | 研发负责人 |
| SOLUTION_REVIEW | 方案评估中 | 尚未决策的产品/测试评估人 |
| READY_FOR_DEV | 待开发 | 研发负责人 |
| DEVELOPING | 开发中 | 研发负责人 |
| READY_FOR_TEST | 待测试 | 测试负责人 |
| TESTING | 测试中 | 测试负责人 |
| ACCEPTANCE_PENDING | 待验收 | 产品负责人 |
| CLOSED | 已关闭 | 无 |
| CANCELLED | 已取消 | 无 |

不另外引入含义重复的“待评估方案”状态。研发提交方案即进入“方案评估中”；全部评估通过进入“待开发”，实际开始开发后才计开发时间。

| 动作 | 起点 → 终点 | 操作者与约束 |
|---|---|---|
| SUBMIT_REQUIREMENT | DRAFT → SOLUTION_PENDING | 产品；需求及负责人完整 |
| RETURN_REQUIREMENT | SOLUTION_PENDING → DRAFT | 研发；必须说明缺失信息 |
| SUBMIT_SOLUTION | SOLUTION_PENDING → SOLUTION_REVIEW | 研发；方案字段完整，冻结版本 |
| APPROVE_SOLUTION | SOLUTION_REVIEW → 原状态或 READY_FOR_DEV | 指定评估人；两个槽位均通过后推进 |
| REJECT_SOLUTION | SOLUTION_REVIEW → SOLUTION_PENDING | 任一指定评估人；原因必填，本轮其他审批作废 |
| START_DEVELOPMENT | READY_FOR_DEV → DEVELOPING | 研发；有效评估快照存在 |
| COMPLETE_DEVELOPMENT | DEVELOPING → READY_FOR_TEST | 研发；自测及交接完整，新建测试轮次 |
| START_TEST | READY_FOR_TEST → TESTING | 指定测试负责人；填写测试环境 |
| FAIL_TEST | TESTING → DEVELOPING | 指定测试负责人；失败说明及关联缺陷必填 |
| PASS_TEST | TESTING → ACCEPTANCE_PENDING | 指定测试负责人；测试记录完整，阻断缺陷全部关闭 |
| ACCEPT | ACCEPTANCE_PENDING → CLOSED | 产品；逐项确认验收标准 |
| REJECT_ACCEPTANCE | ACCEPTANCE_PENDING → DEVELOPING 或 READY_FOR_TEST | 产品；指定原因和去向，新建测试轮次或等待再次提测 |
| APPLY_REQUIREMENT_CHANGE | 非草稿且非终态 → SOLUTION_PENDING | 产品确认变更；生成需求版本并使当前方案审批失效 |
| CANCEL | 任一非终态 → CANCELLED | 产品；必须说明原因 |

终态不直接重开。后续修订创建关联的新任务，保留原交付记录。产品可确认责任转交，但不能替研发提交方案或替测试判定通过。

### 阻塞与需求变更

阻塞包含原因、设置人、设置时间，可由当前负责人设置/解除，产品负责人可代为处理并写明说明。阻塞期间禁止正常向前动作，允许退回、需求变更、取消、责任转交和评论。解除后继续原阶段。统计同时提供阶段总时长和扣除阻塞后的净时长。

产品、研发、测试可提出需求变更草稿。只有产品负责人可确认；确认时必须写清变更内容、原因及范围影响。确认后创建不可变需求版本，废止未完成测试轮次和当前审批，返回待出方案。旧记录保留。普通评论、错别字说明不能直接覆盖已提交的需求快照。

## 4. 业务字段

| 区域 | 关键字段与必填时机 |
|---|---|
| 需求 | 标题、背景、目标、需求描述、可逐项确认的验收标准、优先级、责任人；提交时必填 |
| 方案 | 方案正文、影响范围、工作量（人日）、风险说明、预计开始/结束时间；提交评估时必填 |
| 评估 | PRODUCT/QA 槽位、评估人、结论、意见、方案版本、需求版本；退回意见必填 |
| 开发 | 开发说明、代码/PR 链接（可选）、自测结果、交付版本、可访问环境地址或环境说明、已知问题；提测时必填 |
| 测试 | 轮次、环境、执行记录、结论、缺陷关联、部署验证说明；结论提交时必填 |
| 验收 | 每项验收标准结果、意见、验收人、时间；全部标准通过才可关闭 |

优先级使用 P0/P1/P2/P3，定义为紧急/高/中/低，不与缺陷严重程度混用。缺陷类型 BUG，严重程度为 BLOCKER/MAJOR/MINOR；关联父任务及测试轮次，复用任务交付流程。阻断缺陷必须完成测试并关闭，或经产品与测试共同确认降级且留审计。

## 5. 页面与交互

- 工作台：我的待办、我负责的任务、被阻塞和逾期任务。评估中为两个未决槽位分别生成待办。
- 项目：概览、任务列表、阶段看板、文档、成员设置；归档项目只读。
- 任务列表：分页，支持状态、负责人、优先级、阻塞、关键词过滤。
- 看板：按业务状态分列；拖拽仅在权限及动作允许时开放，需要填写信息则打开动作表单。
- 详情：流程条、当前处理人、允许动作；需求、方案/评估、开发、测试/验收、动态分区。
- 站内通知：分配/转交、方案待评估、退回、提测、测试完成、待验收、@提及。
- 文档：Markdown 编辑、安全预览、版本历史、关联任务；乐观锁防覆盖，冲突时提示重新加载或复制本地内容。

第一版通知采用页面轮询，业务成功提交后下次轮询可见；不依赖 WebSocket。到期提醒与外部邮件作为后续功能，不作为本版验收条件。

## 6. 架构与目录

采用模块化单体 API 和独立 Web 应用。前后端通过同源 `/api/v1` 通信，开发期由 Vite 代理。PostgreSQL 存储业务、会话和通知；无须 Redis 或消息队列。

```text
apps/web/              React + TypeScript + Vite + Ant Design
apps/api/              NestJS REST API
packages/contracts/    DTO、业务枚举与共享契约（不含数据库实体）
prisma/                Schema、迁移、演示数据
tests/e2e/             浏览器业务场景
docs/                  设计和实施提示词
docker-compose.yml     本地数据库
.env.example           无真实密钥的配置示例
```

后端模块：auth、workspaces、projects、tasks、solutions、reviews、testing、documents、comments、attachments、notifications、audit、metrics。状态机和授权集中在领域服务，控制器不直接更新任务状态。

## 7. 数据模型

所有项目业务实体均带 workspaceId；子记录通过复合外键或服务端受控关联确保 workspaceId/projectId 一致。ID 使用 UUID，时间存储 UTC，界面按用户时区展示，默认 Asia/Shanghai。

| 实体 | 核心字段与关系 |
|---|---|
| User / Session | 用户、密码摘要；会话 token 摘要、到期时间、撤销时间 |
| Workspace / WorkspaceMember | 团队；成员身份 ADMIN/MEMBER，唯一 workspaceId+userId |
| Invitation | 团队、目标邮箱、token 摘要、到期时间、接受时间；一次性邀请链接 |
| Project / ProjectMember | 项目、团队、归档时间；成员及多角色集合 |
| Task | 项目、项目内编号、类型、状态、责任人、priority、dueAt（计划截止时间）、version、当前需求/方案/测试轮次指针 |
| RequirementRevision | taskId、递增版本、结构化需求及验收标准、提交人；提交后不可变 |
| RequirementChange | 提议内容、原因、发起人、产品决定、对应需求版本 |
| SolutionRevision | taskId、需求版本、方案版本、正文、估算、风险、排期、提交时间 |
| ReviewRound / ReviewDecision | 绑定需求与方案版本；两个槽位、评估人、结果；唯一 roundId+slot |
| DevelopmentSubmission | taskId、提测序号、开发说明、自测、交付版本、环境、提交人 |
| TestRun / TestRecord | 提测关联、轮次、状态、环境、测试执行内容、结论及执行人 |
| TaskRelation | 父任务、缺陷任务、测试轮次、关系类型；禁止跨项目及自关联 |
| Acceptance | taskId、需求版本、逐项验收结果、产品结论 |
| BlockPeriod | taskId、原因、开始/结束时间、操作人 |
| TaskTransition | 前后状态、动作、操作者、原因、版本、时间 |
| Comment / Mention | 任务评论、作者、提及成员；仅允许提及可访问当前任务的项目成员 |
| Attachment | 资源归属、随机存储键、原文件名、MIME、大小、上传人 |
| Document / DocumentRevision | 项目文档、当前版本、Markdown 内容、作者；提交版本不可变 |
| Notification | 收件人、事件类型、资源 ID、去重键、已读时间 |
| AuditEvent | 团队、资源、操作、操作者、必要字段变更；不写密码/会话/邀请 token |
| IdempotencyRecord | userId、key、请求摘要、结果、到期时间 |

约束：任务编号在项目内唯一；方案和需求版本在任务内唯一；测试轮次在任务内唯一。Task 建立 projectId+status、projectId+priority、责任人、updatedAt 索引；历史按 taskId+createdAt 索引；通知按 recipientId+readAt+createdAt 索引。

需求默认软删除至回收站，可恢复至删除前状态，保留历史、附件、文档和分身引用。创建人、需求负责人或团队管理员可删除/恢复；归档项目只读。永久删除仅限管理员，需输入标题且不存在关联引用。项目使用归档。

## 8. API 约定

统一前缀 `/api/v1`，列表使用 page/pageSize（默认 20，上限 100），返回 items、total、page、pageSize。错误格式包含 code、message、fieldErrors、requestId。

| API | 用途 |
|---|---|
| POST /auth/login，POST /auth/logout，GET /auth/me | 登录、退出、当前会话 |
| GET/POST /workspaces | 我的团队、创建团队 |
| POST /workspaces/:id/invitations，POST /invitations/accept | 创建邀请链接、接受邀请；MVP 不自动发送邮件 |
| GET/PATCH /workspaces/:id/members | 团队成员与管理 |
| GET/POST /workspaces/:id/projects | 项目列表、创建 |
| GET/PATCH /projects/:id，GET/POST/PATCH /projects/:id/members | 项目详情、设置、成员和角色 |
| GET/POST /projects/:id/tasks | 筛选任务、创建草稿 |
| GET/PATCH/DELETE /tasks/:id | 详情、受限编辑、移入回收站 |
| POST /tasks/:id/solutions | 保存或提交新方案版本草稿 |
| POST /tasks/:id/actions | 统一业务动作，处理状态推进与评估 |
| POST /tasks/:id/requirement-changes | 提出需求变更 |
| POST /tasks/:id/blocks，POST /tasks/:id/blocks/:blockId/resolve | 设置与解除阻塞 |
| GET/POST /tasks/:id/comments | 评论与提及 |
| POST /tasks/:id/attachments，GET /attachments/:id/download | 上传、鉴权下载 |
| GET /tasks/:id/timeline | 流转、审批、变更等统一时间线 |
| GET/POST /projects/:id/documents，GET/PATCH /documents/:id | 文档列表、创建、读取、提交版本 |
| GET /documents/:id/revisions | 文档历史 |
| GET /me/todos，GET /notifications，POST /notifications/:id/read | 待办和通知 |
| GET /projects/:id/metrics | 阶段耗时、退回、逾期、交付周期 |

动作示例：

```json
{
  "action": "COMPLETE_DEVELOPMENT",
  "expectedVersion": 7,
  "payload": {
    "summary": "完成需求实现",
    "selfTest": "已验证验收项 1～3",
    "releaseVersion": "demo-0.1",
    "environment": "本地演示环境",
    "knownIssues": "无"
  }
}
```

动作请求头必带 `Idempotency-Key`。业务写入在事务中检查 expectedVersion 并使用条件更新；并发冲突返回 409，事务回滚，不产生部分审批或通知。两个评估人并发通过时，冲突方刷新重试即可，不能丢失审批。

同一用户的相同幂等键和请求内容返回原结果，不重复创建记录；同键不同内容返回 409。幂等记录保留至少 24 小时。前端收到版本冲突后展示最新状态，保留用户输入，不自动盲目重试有业务含义的动作。

## 9. 一致性与安全

- 业务更新、审批、测试轮次、流转、审计、站内通知在同一数据库事务提交。
- 密码使用 Argon2id，登录限流；Session 使用随机 token，数据库仅存摘要。
- Cookie 使用 HttpOnly、SameSite=Lax，生产启用 Secure；所有 Cookie 鉴权写操作校验 CSRF token 和 Origin。
- 服务端校验所有 DTO、资源归属、文件类型和长度；Markdown 禁止原始 HTML 或执行严格净化。
- 附件上限 20MB，MVP 允许 PNG/JPEG/PDF/TXT/DOCX/XLSX/ZIP，检查扩展名、MIME 和适用的文件签名，不执行上传内容。ZIP 不自动解压。
- 附件使用随机存储键，禁止直接暴露文件路径；下载通过当前权限校验，以 attachment 响应并设置 nosniff。
- 文件写入与数据库无法共用事务：先写临时目录，验证后落盘，再保存元数据；失败清理文件，定期清理无引用文件。
- 日志记录 requestId、业务资源及错误码，过滤凭据、Cookie、敏感正文和 token。
- 自动化测试使用独立数据库；迁移、备份恢复和破坏性命令必须显式指定目标环境。

## 10. 统计定义

- 阶段总耗时：每次进入阶段至离开阶段的时间；重复进入分段累计，当前阶段计算至查询时间。
- 阶段净耗时：总耗时减去与该阶段重叠的阻塞区间；时间区间按交集计算，禁止重复扣减。
- 需求交付周期：首次提交需求至最终关闭的自然时间；取消任务单列，不混入已交付统计。
- 方案退回次数：REJECT_SOLUTION 动作数量；测试退回次数：FAIL_TEST 动作数量。
- 逾期：非终态任务当前时间超过计划截止时间；未设置截止时间不计逾期。
- 工作量为估算人日；阶段耗时为自然小时，两者分别展示。

## 11. 测试与验收

| 场景 | 验收结果 |
|---|---|
| 正常交付 | 产品提交 → 研发方案 → 产品/测试分别通过 → 开发 → 提测 → 测试 → 验收关闭，刷新后数据完整 |
| 评估未齐 | 仅一槽位通过仍在评估中，禁止开始开发 |
| 评估分离 | 同账号占两个槽位、方案提交人审批、非指定人审批均被服务端拒绝 |
| 方案退回 | 意见必填，回待出方案，重新提交后两个槽位均需评估 |
| 需求变更 | 开发或测试中确认变更后回待出方案，旧审批失效，旧版本可追溯 |
| 测试失败 | 必须有关联缺陷，回开发中，再提测产生新轮次，历史结论保留 |
| 验收退回 | 返回指定阶段并产生新的测试轮次，不能沿用旧测试结果直接关闭 |
| 阻塞 | 保留业务阶段，禁止前进，解除后恢复；净耗时正确扣减 |
| 并发与幂等 | 重复提交无重复记录；过期版本返回 409；并发评估重试后正确汇合 |
| 数据隔离 | 猜测其他团队任务/文档/附件 ID 无法读取或修改，列表与统计无泄漏 |
| 事务失败 | 注入写入错误，任务、审批、审计、通知全部回滚 |
| 文档冲突 | 两人基于同版本编辑，第二次提交提示冲突，不覆盖第一份结果 |
| 成员与归档 | 有未完成责任时不能直接移除成员；归档后业务写入被拒绝 |
| 基础交互 | 表单错误、无权限、加载失败、空数据和冲突均有明确提示 |

测试分层：状态机和权限单元测试；真实隔离 PostgreSQL 的 API 集成测试；浏览器端到端测试覆盖正常闭环与测试失败退回闭环。测试数据必须包含两个团队及各角色账号，以验证越权访问。

## 12. 本地交付与后续演进

交付应支持 `pnpm install`、启动数据库、执行迁移与种子、`pnpm dev`。仓库提供 `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm test:e2e`、`pnpm build`，脚本名称与 README 保持一致。

演示数据包括两个隔离团队、产品/研发/测试/运维账号、处于各阶段的任务，以及至少一个方案退回、测试失败、阻塞和变更案例。演示账号只用于本地，密码通过本地种子配置生成或显式设置，不用于生产。

上线前提供数据库及附件配套备份和恢复说明，并在隔离环境验证恢复；配置 HTTPS、持久化存储、日志留存及健康检查。生产上线需用户明确授权，不作为当前文档生成任务的执行范围。

后续可按实际使用增加上线验证阶段、WebSocket、外部通知、全文搜索、多人文档编辑与可配置流程。保持现有历史及审计语义兼容。


### 2026-10-16 人员职责分配修订

按用户最新要求，需求中的产品、研发、测试及评估职责从当前项目成员中自由选择，不按成员预设身份筛选。同一成员可兼任多个工作职责，执行任务时按该需求的实际指派授权。团队/项目成员资格与管理权限仍独立校验；两位评估人必须不同，方案提交人不能审批自己的方案，评估进行中不能更换评估人。

责任转交不要求填写原因；服务端自动记录“调整需求责任分工”并沿用事务、版本冲突、幂等与通知机制。右侧基本信息支持优先级、计划截止和责任人的行内弹层修改；项目迁移、迭代及任务类型转换不在此处开放。

新增 PATCH /tasks/:id/properties 只接受 expectedVersion、priority 和可为空的 dueAt；仅当前产品负责人可修改，归档和终态只读。基本信息更新追加历史并产生审计与站内通知。状态选择展示允许的业务动作，仍通过动作表单和状态机处理。
