# CoFlow 版本号与更新规范

## 编号

使用 `主版本.功能版本.修订版本`，例如 `v2.1.3`。整个产品只有一个对外版本，同时分别记录前端和后端组件版本。变更类别独立记录，不能靠日期或 FE/BE 后缀代替版本大小比较。

| 字段 | 用途 | 示例 |
| --- | --- | --- |
| product | 对外产品版本，每轮完成的更新必须递增 | 2.1.3 |
| web | 前端组件版本，仅前端变化时递增 | 2.1.2 |
| api | 后端组件版本，仅后端变化时递增 | 2.0.4 |
| categories | 本轮变更分类，可多选 | frontend、backend、feature、maintenance |
| status | 当前版本状态 | draft、validated、released |

功能更新是变更的性质，不是与前后端平行的第三个组件。同一轮新增功能可以同时标记 `feature + frontend + backend`。

## 何时递增

| 改动 | 产品版本 | 涉及组件版本 | 分类 |
| --- | --- | --- | --- |
| 配色、字号、间距、提示文案、布局优化，不改变业务能力 | PATCH +1 | web PATCH +1 | frontend |
| 修复接口、权限、性能、启动或部署问题，兼容原有用法 | PATCH +1 | api PATCH +1；仅部署脚本时组件可不变 | backend 或 maintenance |
| 新增能力或改变可感知的业务操作流程，兼容旧数据与接口 | MINOR +1，PATCH 归零 | 实际新增能力的组件 MINOR +1 | feature，加实际涉及的 frontend/backend |
| 重大产品里程碑升级，或接口/数据/部署方式不兼容 | MAJOR +1，MINOR/PATCH 归零 | 不兼容的组件 MAJOR +1 | 实际涉及的分类，并说明迁移方式 |
| 只改开发说明、规范或发布元数据 | PATCH +1 | web/api 不变 | maintenance |

多类改动在同一轮交付时，按最高影响级别递增一次。两个组件版本独立判断，不要求与产品版本相同。重大产品里程碑也递增产品 MAJOR，即使兼容旧接口；组件版本按实际影响递增。

“每轮”指一次可交付、已完成验证的修改集合，不是每次保存文件、每次工具调用或每次重新构建。用户验收后再次修改，即使仅调整一档颜色，也视为新一轮，必须升版。修复尚未交付版本内发现的问题，可继续使用该草稿版本；已标记 released 的版本不可覆盖重发。

## 示例（均从基线独立举例，不代表已经发布）

| 更新 | product | web | api | categories |
| --- | --- | --- | --- | --- |
| 版本基线 | 2.0.0 | 2.0.0 | 2.0.0 | maintenance |
| 学生端绿色加深 | 2.0.1 | 2.0.1 | 2.0.0 | frontend |
| 修复兼容性的接口错误 | 2.0.1 | 2.0.0 | 2.0.1 | backend |
| 新增前后端联动的发布管理 | 2.1.0 | 2.1.0 | 2.1.0 | feature、frontend、backend |

## 每轮执行顺序

1. 开始前读取根目录 `version.json` 与 `CHANGELOG.md`，确定当前版本及本轮范围。
2. 完成修改后，按表中规则更新产品及涉及组件版本、分类和北京时间日期，状态设为 draft。
3. 在 CHANGELOG.md 顶部增加条目：版本、类别、用户可感知的变化、验证结果、兼容性或迁移要求。未执行的检查不能写为通过。
4. 相关检查通过后改为 validated；无法完成验证时保留 draft，并明确原因。
5. 只有实际部署完成并验证运行版本与健康检查后，才能标记 released。构建成功不等于发布成功。
6. 每次向用户交付必须说明版本号、前端/后端/功能分类，以及是否已部署。

## 打包与追踪

推荐包名：`CoFlow-v2.1.3-web2.1.2-api2.0.4.zip`。预发布版本可使用 `2.1.3-rc.1`，正式版移除预发布后缀。

现有打包脚本的 manifest.id 是安装与校验用标识，应继续保留；版本号是新增的产品发布语义，两者不能混为一谈。本次只建立规范和版本基线，现有自动更新程序尚未自动读取 version.json；接入发布脚本时必须另外验证，不能宣称已实现自动升版或自动拦截降级。

根目录 version.json 为版本台账的唯一来源；package.json 如声明组件版本应同步。开发文档中的需求版本、任务数据 version、方案版本、API 路径 /v1 均与产品发布版本独立。

## 产品里程碑与当前基线

根据用户确认的产品历史：
- v1：学生版与企业版分离。
- v2：增加项目分身（决策分支）及自回归优化流程。
- v3：用户于2026-10-20确认，全项目按业务模块重构，企业版与学生版拆分独立前端入口和构建，共享业务内核，版本切换统一迁入设置。
- v4：用户于2026-10-21确认，以AI推进项目及专业团队协作交付为主线；首批实现基于真实需求的推进建议、依据核对和行动草稿交接，后续逐步扩展执行与复盘。

用户将已有产品基线指定为 product/web/api 2.2.0；这是编号登记，不补造 2.1.x 至 2.2.0 的逐次历史。先前拟定的 2.0.0 台账初值被此次指定替代。v1、v2 的里程碑定义保持有效。

本轮原规划的前端 2.2.1 尚未交付，随后并入多团队加入和成员管理分离功能，按最高影响统一升为 product/web/api 2.3.0，不产生独立发布的 2.2.1。当前值与验证状态以 version.json 为准。登记日期不代表历史发布日期，未实际部署不得标记 released。
