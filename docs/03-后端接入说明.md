# 汇流 后端接入说明

日期：2026-10-16。API 前缀 `/api/v1`，开发期浏览器经 Vite 同源代理访问。

## 会话与邀请

1. `POST /auth/login`，JSON 为 `{email,password}`，需要与 `APP_ORIGIN` 相同的 Origin。响应包含 `user` 和 `csrf`，设置 HttpOnly、SameSite=Lax Cookie。
2. `GET /auth/me` 恢复会话和 CSRF token；`POST /auth/logout` 撤销会话。
3. 所有已登录写操作携带 Cookie、Origin、`X-CSRF-Token`。会话固定 24 小时到期，生产启用 Secure Cookie。
4. 管理员 `POST /workspaces/:id/invitations`，JSON `{email}`，返回 7 天有效链接，不发送邮件。
5. 未注册用户：`GET /invitations/:token/preview` 读取邀请信息；`POST /auth/register-invitation`，JSON `{token,name,password}`，密码至少 12 位，成功后自行登录。注册与邀请领取为一个事务。
6. 已有账号登录后：`POST /invitations/accept`，JSON `{token}`，邮箱必须匹配。一次性领取，不自动获得项目成员身份；由管理员分配项目及角色。

## 团队与项目

团队：`GET/POST /workspaces`、`GET/PATCH /workspaces/:id/members`。

项目：`GET/POST /workspaces/:id/projects`、`GET/PATCH /projects/:id`；PATCH 支持 `{name?,archived?}`。归档后业务只读，管理员可以恢复项目。

项目成员：`GET/POST /projects/:id/members`，保存体 `{userId,roles:[PRODUCT|ENGINEER|QA|OPS]}`，更新采用同一 POST upsert；`DELETE /projects/:id/members/:userId`。有未结束责任不能移除成员或撤销所需角色。

## 任务与业务动作

`GET /projects/:id/tasks` 支持 `page/pageSize`（20/100）、`status`、`priority`、`blocked=true|false`、`owner=<用户ID>`、`q`；返回 `{items,total,page,pageSize}`。

`POST /projects/:id/tasks` 创建草稿，字段：`title/background/goal/description/criteria[]/priority/productId/engineerId/productReviewerId/qaReviewerId/testerId/dueAt?`。缺陷额外指定 `type=BUG`、`severity`、`parentId` 和 `parentRound`，父任务必须属于本项目且轮次存在。

`GET /tasks/:id` 返回任务、附件摘要、当前 `handlerIds` 和服务端计算的 `allowedActions`。任务细节位于 `data`。前端展示允许动作仍不能代替服务端校验。

`PATCH /tasks/:id` 只编辑草稿的业务字段，必须带 `expectedVersion`。已提交需求不得覆盖，需走变更动作。`DELETE /tasks/:id` 改为移入回收站，创建人、需求负责人或团队管理员可操作，JSON 带 `expectedVersion`。`POST /tasks/:id/restore` 按版本恢复原状态。历史、附件及引用保留；回收站不进入日常列表、待办和交付统计，关联位置可继续读取历史并显示删除标识。归档项目及回收站中的需求禁止业务写入。

`DELETE /tasks/:id/permanent` 仅限团队管理员，必须在回收站，提交 `expectedVersion` 和 `confirmTitle`；文档、缺陷、成果验证或项目分身存在引用时拒绝永久删除。独立审计保留。

新项目支持 `workflow: SIMPLE | STANDARD`，接口缺省为 STANDARD，学生版创建窗口默认 SIMPLE，旧项目及旧需求沿用标准流程。每条需求保存流程快照。简易流程为草稿→待办（READY_FOR_DEV）→进行中（DEVELOPING）→待验收→完成，允许一人兼任，不要求独立评估人；新增 START_WORK 和 SUBMIT_ACCEPTANCE 动作。

创建需求只需标题，默认当前用户为负责人；`POST /projects/:id/tasks` 可带 `submit: true` 在同一事务创建并提交，校验失败时不遗留草稿。标准流程仍保留完整提交校验。列表支持 scope=active/all/mine/handling/overdue/ended/trash，默认展示未结束需求；显式状态筛选保留历史查询能力。当前项目内的团队管理员可代为修改基本属性和转交职责，操作保留历史及版本检查。

所有正式状态操作都使用：

```http
POST /api/v1/tasks/<id>/actions
Idempotency-Key: <每次业务意图生成一个UUID，网络重试沿用>
X-CSRF-Token: <当前会话token>
Content-Type: application/json
```

```json
{"action":"COMPLETE_DEVELOPMENT","expectedVersion":7,"payload":{"summary":"完成需求实现","selfTest":"验收项均通过","releaseVersion":"demo-0.1","environment":"本地演示环境","knownIssues":"无"}}
```

| 动作 | payload |
| --- | --- |
| SUBMIT_REQUIREMENT / START_DEVELOPMENT | `{}` |
| RETURN_REQUIREMENT / REJECT_SOLUTION / CANCEL / BLOCK / UNBLOCK | `{reason}` |
| SUBMIT_SOLUTION | `{body,scope,effort,risk,start,end}`，effort 为正数人日 |
| APPROVE_SOLUTION | `{reason?}`，槽位由当前用户确定 |
| COMPLETE_DEVELOPMENT | `{summary,selfTest,releaseVersion,environment,knownIssues}` |
| START_TEST | `{environment}` |
| FAIL_TEST | `{record,deployment,reason,defectIds:[]}`，关联当前轮次的真实 BUG |
| PASS_TEST | `{record,deployment}`，所有关联 BLOCKER 必须 CLOSED |
| ACCEPT | `{checks:[true,...],opinion?}`，数组逐项对应验收标准 |
| REJECT_ACCEPTANCE | `{reason,target:"DEVELOPING"或"READY_FOR_TEST"}` |
| APPLY_REQUIREMENT_CHANGE | `{description,criteria:[],reason,impact}`，仅产品确认 |
| TRANSFER | `{reason,productId?,engineerId?,productReviewerId?,qaReviewerId?,testerId?}` |

状态枚举及中文名称在 `packages/contracts/index.ts`。方案草稿接口：`POST /tasks/:id/solutions`，JSON `{expectedVersion,payload:{body?,scope?,effort?,risk?,start?,end?}}`。只有待出方案阶段的研发负责人可保存；`submit:true` 时转到相同的 SUBMIT_SOLUTION 事务处理，需要幂等键。评估中不能编辑快照。

阻塞快捷接口：`POST /tasks/:id/blocks`（`{expectedVersion,reason}`）和 `POST /tasks/:id/blocks/:blockId/resolve`（同体），均需要幂等键，内部调用相同动作处理器。

需求变更提议：`POST /tasks/:id/requirement-changes`，JSON `{expectedVersion,description,reason,impact}`，产品/研发/测试项目角色可提出。提议不直接改变需求快照；产品确认时使用 APPLY_REQUIREMENT_CHANGE 明确提交描述、验收标准及影响，新建版本并废止旧审批及未完成轮次。

## 协作与文档

- `GET/POST /tasks/:id/comments`：POST 为 `{expectedVersion,body,mentions:[用户ID]}`，只允许提及当前项目成员。Markdown 原始 HTML 不应执行。
- `POST /tasks/:id/attachments`：multipart `file`，20MB 上限；`GET /attachments/:id/download`：鉴权下载。禁止直接拼接存储路径。
- `GET /tasks/:id/timeline`：按时间排序的流转、评论、变更提议、附件及补充审计事件。
- `GET /me/todos`：当前用户有责任处理的任务；方案评估分别为尚未决策的两个账号提供待办。
- `GET /notifications`：分页；`POST /notifications/:id/read`：标已读。前端每 15 秒轮询即可。
- `GET/POST /projects/:id/documents`：创建体 `{title,content,taskIds:[]}`；`GET/PATCH /documents/:id`：修改额外带 `expectedVersion`；`GET /documents/:id/revisions`：不可变版本数组。
- `GET /projects/:id/metrics`：各任务阶段总/净自然小时、方案/测试退回次数、逾期及已关闭交付周期；取消任务不计交付周期。

任务与通知列表采用分页对象；团队、项目、成员、文档、时间线和待办目前返回数组。接口前端适配应遵守这些实际返回类型。

## 错误处理

错误响应 `{code,message,fieldErrors?,requestId}`。401 重新登录；跨团队资源 404；同团队非项目成员/非指定角色操作 403；输入错误 422；版本或幂等冲突 409；大小超限 413。500 只返回通用消息，日志仅含 requestId、错误码及状态。

409 时刷新任务状态并保留表单输入；让用户明确决定下一次提交，不自动重放审批、提测或关闭动作。相同用户相同幂等键与请求内容返回首次结果；同键不同内容 409。

## 文档关联任务选项

GET /api/v1/projects/:id/task-options 使用与项目资源相同的成员权限校验，支持 page 和 pageSize（1–100，默认20）。返回 page、pageSize、total、items；每项仅含 id 和 title，按任务编号升序。无项目访问权限返回404。此接口用于文档关联选择，不替代带完整业务字段的任务接口。

## 文档与需求关联读取

GET /api/v1/tasks/:id/documents 返回同项目内关联此需求的文档元数据；GET /api/v1/documents/:id/tasks 返回同项目内关联需求的 id、number、title、status。均先校验项目访问权限，无权限返回404。文档关联仍通过现有文档创建/修改接口的 taskIds 管理，沿用 expectedVersion 冲突与归档只读规则。

## 项目需求模板

GET/POST /api/v1/projects/:id/templates，PATCH /api/v1/templates/:id。列表返回items、canManage、readOnly，普通项目成员仅可读取已启用模板；团队管理员或项目产品成员可写，归档只读。写入参数为name、content、active；修改还需expectedVersion。content只允许title、background、goal、description、criteria、priority。写入与TEMPLATE_CREATE/TEMPLATE_UPDATE审计同事务提交。详情见docs/10-需求模板中心与企业应用规划.md。

## FirstStepAgent

POST /api/v1/competitions/:id/firststep/preview、run、save。preview无需Key；个人设置/settings/ai/verify验证已保存Key；run从当前用户设置读取Key，要求consent=true，默认DeepSeek Flash；save带expectedVersion和requestKey，六份文档同事务及幂等保存。均校验项目权限，归档仅可预览。详细字段、错误、脱敏和使用边界见docs/12-FirstStepAgent竞赛启动助手.md。

### ProofLoop

GET /api/v1/competitions/:id/proof 返回主张、证据、动态状态、文书和补证任务状态。
POST 同路径/claims 保存主张（claim、可选claimId、expectedVersion）；证据指定同项目documentId、version及连续原文quote。importance为1—5，effortHours为0.5—80。
POST /check 指定2—6个documentIds、expectedVersion、consent=true，使用当前账号保存的DeepSeek配置；拒绝重复文书、越权、过大输入、无原文依据的模型引用、并发换版和归档写入。
POST /review 接收claimId、expectedVersion、outcome=SUPPORTED/REFUTED及至少20字note；核对人由会话确定，需当前有效证据和验证条件。
POST /task 接收itemId、kind=CLAIM/FINDING、expectedVersion及owners（5个角色），同事务创建普通需求草稿并关联条目，重试同一条目返回原任务。
GET /export 在RepeatableRead事务中生成JSON快照及Markdown摘要，重新核对项目和团队成员资格。仅含关联或检查过的文书，支持归档读取。摘要仅用于完整性验证，不能用于证明事实真实性。


## 阶段文件解析与填入

`POST /ai/import` 保持 `{kind,text,consent:true}` 输入与 `{fields,model}` 输出；kind 在 project/requirement 之外新增 solution、development、testing、testEnvironment、simpleDelivery。只提取当前种类的正文、范围、工作量、排期、自测、交付版本、环境、已知问题及测试记录等资料字段，服务端拒绝跨种类或流程字段。原有个人凭据、发送同意及频率限制继续生效。

本地解析无需模型Key；支持8MB以内的TXT、Markdown、DOCX和文字型PDF，最多6万字符，扫描件仍需先OCR。已上传附件使用现有鉴权下载接口读取，不公开存储路径。原文提取不猜测工作量、相对日期和测试结论。解析只填入待提交表单，不调用业务流转接口；人工确认提交时继续按原权限和expectedVersion校验。

## 团队成员管理

- `PATCH /workspaces/:id`：管理员修改团队名称 `{name}`。
- `GET /workspaces/:id/members`：返回团队显示名 `name`、账号原名 `accountName`、可空 `displayName`、邮箱及团队角色。
- `PATCH /workspaces/:id/members/:userId`：管理员修改 `{displayName,role?}`；显示名为空恢复账号原名，不允许修改登录邮箱。团队角色仍兼容原 `/members` PATCH 接口。
- `GET /workspaces/:id/members/:userId/projects`：管理员查看本团队项目及该成员的项目角色；`POST .../move` 接收 `{sourceId?,targetId,roles}`，不传来源表示新增分配，传来源则原子移动，合并目标已有角色。
- `GET /workspaces/:id/member-transfer-targets`：仅返回操作者管理的其他团队；`POST /workspaces/:id/members/:userId/transfer` 接收 `{targetWorkspaceId}`，要求两边管理员权限，不迁移原团队的需求或历史。
- `DELETE /workspaces/:id/members/:userId`：移出团队并删除其项目成员身份、当前团队QQ绑定/绑定码及待接受的邮箱邀请，保留账号、业务历史及其他团队成员身份。移出不构成账号封禁，仍可凭有效团队码重新加入。

移动来源项目或移出团队前检查所有未结束需求的五类负责人（包括回收站）；最后一位团队管理员不可降级、移出或转移。成员变更使用事务内权限重查、团队/项目行锁及审计记录。跨团队转移在同一事务内撤销来源成员资格并加入目标，目标已有身份保留，新加入角色为 MEMBER。

部署前执行 `prisma migrate deploy` 应用 `20261018020000_team_member_management`，只新增可空的团队显示名，不改写已有账号。
